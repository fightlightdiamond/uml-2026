> **Edition:** 1.7

> **Audience:** backend developers, database developers, technical leads, and solution architects  
> **Companion workbook:** `sql/2.md`

## Purpose

This handbook builds a production-oriented mental model of SQL Server. Each mechanism has one authoritative module. Later modules reuse it by naming that owner, and do not teach it again.

# Part 0 — How to Reason About SQL Server

## Requirement → Mechanism → Evidence

Start with the business invariant, service objective, or operational promise. Identify the SQL Server mechanism that can enforce or violate it. Select evidence that can falsify the leading hypothesis. Only then choose a change.

## Diagnostic Evidence Contract

A diagnosis records the time window, workload identity, baseline, observed facts, competing hypotheses, missing evidence, decision threshold, success criterion, and rollback trigger. A wait name, plan operator, recommendation, or elapsed-time value is evidence, not a self-proving conclusion.

Each module below names the evidence and the falsifier for its own scenario.

## Production Change Contract

Every production change states expected benefit, shifted cost, correctness risk, blast radius, validation method, owner, expiration or review date, and rollback path. Prefer the smallest reversible change that preserves evidence.

## Quantitative Baseline

Use Little’s Law, `L = λW`, where this handbook owns a queue: locks, memory grants, TempDB consumers, workers, and incident amplification. Arrival rate, residence time, and concurrency stay tied together. Modules whose cost is space, pages, duration, or a recovery window quantify that unit directly.

## Common Exit Rubric

A learner passes a module when the explanation connects requirement → mechanism → evidence → trade-off → rollback, distinguishes fact from inference, and quantifies the cost that module owns.

## Module 15 — Integrity, Backup, Restore, and Disaster Recoverability

### Learning Outcomes

Learners can explain the mechanisms below, predict their failure modes, select diagnostic evidence, and make a reversible production decision.

### Authoritative Scope

- recovery models as the input to backup policy and to whether log truncation waits for a log backup.
- full, differential, and log backups.
- tail-log decisions.
- restore chains ordered by LSN.
- point-in-time recovery.
- RPO and RTO.
- DBCC CHECKDB.
- backup encryption.
- certificate and key custody.
- isolated restore validation.

### Mental Model

Track state, who owns the resource, where the memory/disk boundary sits, and what an outsider can observe. A feature name or a single counter is not a health verdict.

### Production Scenario

The database uses the FULL recovery model. A full backup finishes Sunday 01:00. A differential finishes Wednesday 01:00. Log backups run every five minutes. On Thursday at 10:37 a bad change is discovered. Recover to Thursday 10:32.

Use the Wednesday differential as the latest base taken before the stop time. Apply only log backups whose LSN range follows that differential, then stop at Thursday 10:32. Take a tail-log backup when the log is available. If the backups are encrypted, the restore instance needs the protecting certificate. SIMPLE recovery cannot restore to this point in time. A differential taken after Thursday 10:32 cannot be the base for that stop time. BULK_LOGGED recovery can also block point-in-time recovery across a minimally logged operation.

### Diagnostic Evidence

Record the recovery model, each backup’s first and last LSN, whether the chain from the Wednesday differential through Thursday 10:32 is unbroken, the tail-log result, and certificate availability. The chain is unusable when an LSN gap appears, or when a minimally logged operation under BULK_LOGGED sits inside the stop window.

### Failure Modes and Trade-offs

Document the primary failure mode, one competing cause, the cost shifted by the proposed fix, a condition under which the fix becomes harmful, and the rollback trigger.
